# 1. Orientation

The big picture: what Sentinel is for, its parts, how to run each one, and a map of the repository.

## What you will learn

- What Sentinel gives a satellite operator, in the operator's own terms, and where the evidence for each claim lives.
- The twelve parts of the system, what each one is for, and which chapter covers it.
- How one Python package becomes a standalone node, a hub or an edge, by configuration alone.
- Where everything lives: every top-level directory and every package under `sentinel/`.
- How to run each piece, from one unit test to two nodes over a shaped link.
- How `.importlinter` states the architecture in eleven rules that CI enforces.

## Why it exists

### The operator's problem

A satellite operator receives warnings that a tracked object may pass close to one of their spacecraft. Each warning is a Conjunction Data Message (CDM). The same event is warned about several times, as tracking improves. Before a deadline called the maneuver commit point, the operator must decide: spend propellant to move, or not.

Sentinel is a decision aid for that call. The README's section "What it gives an operator" makes five promises. Each one is a part of the code you will read.

| Promise | What it means in the code | Evidence |
|---|---|---|
| **No false reassurance.** A low probability of collision (Pc) can mean "we barely know where either object is". | The risk engine detects that dilution and reports the worst case. Where its model does not apply it refuses, with a named reason, instead of printing a number. | [`docs/validation-report.md`](../validation-report.md): the engine against NASA CARA's published cases |
| **The most urgent data crosses a thin link first.** | The edge pulls summaries of every event first, then full CDMs in order of their commit points. | [`docs/ddil-results.md`](../ddil-results.md), LIMITED |
| **It keeps working disconnected.** | Each node serves its own console. Decisions made offline merge without loss, and conflicting edits are shown. The edge recomputes the hub's numbers before it calls them VERIFIED. | [`docs/ddil-results.md`](../ddil-results.md), DENIED and RECOVERY |
| **It is built for the approval path.** | Signed bundles verified offline, SBOMs and VEX, a requirement trace and an OSCAL package generated from test evidence. | [`docs/supply-chain.md`](../supply-chain.md), [`docs/compliance.md`](../compliance.md), [`docs/traceability.md`](../traceability.md) |
| **A ground unit learns when public imagers can see it,** and its position never leaves its node. | The pass module runs at the edge. The unit is never a sync record, and the edge's NATS server refuses to export its subjects. | [`docs/ddil-results.md`](../ddil-results.md), OPSEC |

The AI assistant is left off that list on purpose. It is a safety pattern: the model routes a request and phrases the answer, and Sentinel's own code computes every number ([chapter 11](11-ai-assistant.md)).

The numbers behind each promise are measured and regenerated by `make` targets. They move when the code moves, so this course never copies them. Read them in the generated reports.

### The limits, stated as plainly

Sentinel is a demonstrator. It runs on NASA CARA's published CDMs, a scripted exercise labelled EXERCISE, and a public CelesTrak snapshot. Nothing is fielded, no ATO is claimed, and the DDIL numbers come from real processes on one machine with the link shaped by Toxiproxy. The README's "Limits" section and `SECURITY.md` list the open gaps. Keep them in mind when you explain a design choice: the architecture is proven with measurements; the operational capability is not.

### Why this chapter

The repository is large: about twelve thousand lines of Python under `sentinel/` alone, plus the console, the harness, deployment and compliance code. You do not need to read it all to change it safely. You need a map: which part does what, which parts may depend on which, and which check fails when you break a rule.

## Concepts

### Words you will meet everywhere

| Term | Meaning here |
|---|---|
| Conjunction | Two objects predicted to pass close to each other |
| TCA | Time of closest approach |
| CDM | CCSDS 508.0-B-1 Conjunction Data Message: both objects' states and covariances at TCA, as key = value text |
| Covariance | The uncertainty of a position, as a 3×3 matrix in m² |
| Pc | Probability of collision, from integrating that uncertainty over a disk the size of both objects |
| Dilution | The regime where *more* uncertainty gives a *lower* Pc. A low Pc there is not evidence of safety |
| Refusal | The engine declines to give a Pc, with a `RefusalReason` and the value that tripped the gate |
| MCP | Maneuver commit point: TCA minus 8 hours by default. An operator assumption, labelled as one |
| Band | RED, AMBER, GREEN or UNASSESSED: the Pc sorted against the operator's thresholds |
| Data class | REAL, DERIVED or EXERCISE, carried on every CDM |
| DDIL | Denied, degraded, intermittent or limited: the link states Sentinel is built for |
| Hub, edge | Two roles of the same node. The hub holds the full picture; an edge pulls from it over a bad link |
| CRDT | A data type whose copies merge to the same state whatever order updates arrive in ([chapter 8](08-operator-data.md)) |
| Element set | A TLE or OMM: an orbit good enough for geometry, with no covariance, so never good enough for a Pc |

### One node

Everything runs as one Python process, the *node*, beside its own `nats-server`. The node never talks to another node directly. It talks to its local NATS server, and that server holds the link.

```
 one node (one host)
 ┌───────────────────────────────────────────────────────────────────┐
 │ sentinel serve                                                    │
 │  ┌─────────────────────────────────────────────────────────────┐  │
 │  │ api: HTTP routes, /api/stream (SSE), the built console      │  │
 │  └─────────────────────────────────────────────────────────────┘  │
 │   conjunction ─ cdm ─ risk     ops ─ crdt     passes   ai ─ audit │
 │        │                        │                                 │
 │   sync (SyncServer on a hub, SyncAgent on an edge)   linkstate    │
 │        │                                                          │
 │   bus: in-process, or NATS when SENTINEL_NATS_URL is set          │
 └────────┼──────────────────────────────────────────────────────────┘
          ▼
     nats-server  ◄── the only thing that holds a link to another node
```

`sentinel/api/app.py` builds this. `build_node` creates the clock, bus, store, services and link monitor. The `lifespan` hook then connects NATS, builds the sync records, starts the sync server or agent, loads the NASA library and starts the exercise feeder.

### Three roles, one build

The role is an environment variable, `SENTINEL_ROLE`, not a separate program:

| Role | Starts | Typical place |
|---|---|---|
| `standalone` | no sync; in-process bus unless told otherwise | a laptop, one enclave |
| `hub` | `SyncServer`: answers manifest, fetch and operator-data requests | an operations centre or the cloud |
| `edge` | `SyncAgent`: pulls from the hub named by `SENTINEL_HUB_ID` | a deployed node on a bad link |

`docs/technical-guide.md` has the full configuration reference.

### A hub and an edge

```
  edge node                                               hub node
 ┌──────────────┐                                       ┌──────────────┐
 │ sentinel     │                                       │ sentinel     │
 │ console :8001│                                       │ console :8000│
 └──────┬───────┘                                       └──────┬───────┘
   nats-server ──leafnode── [Toxiproxy in the harness] ── nats-server
        crosses:      sync.<hub>.manifest   summaries of every active event
                      sync.<hub>.fetch      one CDM's original bytes
                      ops.<hub>.exchange    operator data, both ways
        never crosses: node.<id>.>  (console events)   unit.>  passes.>
```

Three rules explain most of the design:

1. **Reference data flows down by pull.** The edge asks for summaries, then for the records that matter most. It re-assesses every CDM itself ([chapter 7](07-priority-sync.md)).
2. **Operator data flows both ways by merge.** Decisions and triage status are CRDTs, exchanged as state ([chapter 8](08-operator-data.md)).
3. **Console events stay home.** Each node publishes on `node.<its id>.>`, and the edge's leaf configuration (`deploy/nats/edge.conf.tmpl`) denies that subject. An edge console never shows a hub number it has not checked ([chapter 6](06-bus-and-links.md)).

## Code walkthrough

A guided tour of the repository, in the order that makes it make sense: the package first, then the things around it.

### `sentinel/`: the package, bottom to top

Read the packages in layers. Each layer may use the ones below it, never the ones above.

**Foundations.** No imports from the rest of `sentinel`.
- `sentinel/risk/`: pure maths. `assess` in `sentinel/risk/engine.py` is the entry point, and it never raises on bad data: it returns `Method.REFUSED` with a `RefusalReason`.
- `sentinel/clock.py`: the `Clock` protocol, with `RealClock`, `SimClock` and `FixedClock`. Every "now" in the node comes from here, which is how tests freeze time.
- `sentinel/obs.py`: `get_logger`. Messages are constant strings and values go in fields (`log.info("Sync cycle failed", hub_id=...)`). `tests/test_logging_policy.py` parses the source and fails on an interpolated message.

**Seams on open standards.**
- `sentinel/cdm/`: the CCSDS CDM codec. `parse_bytes` in `sentinel/cdm/kvn.py` reads structure only; `validate` in `sentinel/cdm/validate.py` decides wrong (raise `CdmRejected`) from incomplete (return a `CdmWarning`); `to_conjunction` builds the engine's input. This is ADR-001's seam: nothing downstream knows where a CDM came from.
- `sentinel/ephemeris/` and `sentinel/adapters/`: CCSDS OEM ephemerides and the one source adapter (Wayfinder, on an assumed schema). They feed the pass module ([chapter 10](10-passes-and-screening.md)).

**The core.** Mission-agnostic: it never names a conjunction.
- `sentinel/bus/`: the `Bus` protocol in `sentinel/bus/base.py`, with `InProcessBus`, `NatsBus` and `LateBus`. `sentinel/bus/subjects.py` is the one place subjects are spelled.
- `sentinel/triage/__init__.py`: one file. `TriageKey` and `order` are the whole vocabulary sync has for "urgent": a class, a deadline and a consequence.
- `sentinel/crdt/`: dots, the signed log (`SignedLog`) and multi-value registers (`MVMap`).
- `sentinel/linkstate/`: `LinkMonitor` classifies the link from what sync observes.
- `sentinel/audit/`: the hash-chained audit log the assistant writes.

**Mission-agnostic platform.**
- `sentinel/sync/`: `SyncAgent` (edge) and `SyncServer` (hub). They see a mission only through the `ReferenceRecords` protocol in `sentinel/sync/records.py`.
- `sentinel/ops/`: `OpsService` persists and exchanges operator data. It asks the mission module whether a decision is still current through a callback, `current_ref`.

**Mission modules.**
- `sentinel/conjunction/`: `ConjunctionService` in `sentinel/conjunction/service.py` is where every CDM enters, by every route. `sentinel/conjunction/policy.py` bands a Pc; `sentinel/conjunction/summaries.py` makes the small summaries that cross a link first; `sentinel/conjunction/exercise.py` is the scripted scenario.
- `sentinel/passes/`: overhead passes for a ground unit.
- `sentinel/screening/`: demonstration mode, element-set geometry that ends as a DERIVED CDM with no covariance.
- `sentinel/validation/`: NASA CARA's published cases, shared by the tier 3 tests, `make report` and the Validation tab.

**Decision support.** `sentinel/ai/`: router, tools, narrators and the grounding guard. Its tools receive the services they read; it has no path to the maths.

**Node assembly.** `sentinel/api/`: the composition root. `build_node` and `create_app` in `sentinel/api/app.py` are the only code that knows every module. `REGISTRARS` in `sentinel/api/extensions.py` mounts the AI, pass and screening routes. `CompositeRecords` in `sentinel/api/records.py` puts several modules behind one sync interface.

**Entry points.** `sentinel/cli.py` (`assess`, `cdm parse`, `cdm emit`) and `sentinel/cli_ext.py` (`serve`, `exercise generate`, `screen`). The split keeps `sentinel assess` free of the web stack. Beside them, `sentinel/localenv.py` loads the gitignored `.env` (template: `.env.example`) for development commands such as `make demo-local` and `make ai-eval`; a variable already exported wins, and a deployed node never reads the file.

*Easy to get wrong:* the composition root is the right place to wire a new module, and the wrong place for its logic. If you find yourself importing a mission module into `sentinel/sync` or `sentinel/ops` to make something work, the contracts below will stop you. Add a callback or a protocol method instead, as `current_ref` does.

### The architecture in miniature: `.importlinter`

Diagrams drift. Import rules do not, because `uv run lint-imports` runs in CI and fails the build. Read the eleven contracts in `.importlinter` as the architecture's shape:

```
 layer              package                  may NOT import
 ─────────────────  ───────────────────────  ─────────────────────────────────────────
 node assembly      api                      (nothing forbidden: it wires everything)
 decision support   ai                       risk, cdm, numpy, scipy
 mission modules    passes                   risk, cdm, conjunction, sync, api, ai,
                                             httpx, nats, fastapi, uvicorn
                    screening                risk, conjunction, api, sync, ai
                    conjunction              (free to use cdm, risk, bus, triage)
 platform and core  sync, ops, crdt,         conjunction, risk, cdm, passes, api
                    linkstate
                    bus, triage              conjunction, risk, cdm, passes, api
 seams              cdm                      conjunction, api, bus
                    ephemeris, adapters      risk, cdm (one exception), conjunction,
                                             sync, api, ai; ephemeris also passes,
                                             adapters
 foundations        risk                     fastapi, nats, sqlite3, httpx
```

The contracts fall into four groups:

| Group | Contracts | The promise |
|---|---|---|
| Purity | `risk-pure`, `passes-offline` | The maths does no I/O; the pass engine needs no network |
| A core that knows no mission | `core-is-mission-agnostic`, `sync-is-mission-agnostic` | A new mission module never edits `sentinel/sync`, `bus`, `crdt` or `triage` |
| Seams | `cdm-is-a-seam`, `ephemeris-and-adapters-are-independent`, `ephemeris-is-below-passes` | Standards sit at the boundaries, below the services that use them |
| Separation of decisions | `ai-does-no-math`, `hosted-ai-at-the-edges`, `screening-never-decides-pc`, `passes-is-independent` | Only the engine decides a Pc; hosted AI SDKs stay in two adapter files |

`include_external_packages = True` at the top is what lets a contract forbid numpy or fastapi, not only Sentinel's own packages. The one exception is written into the file rather than hidden: `ignore_imports` lets `sentinel.ephemeris.oem` use the CCSDS time parser in `sentinel/cdm/timefmt.py`, which CDMs and OEMs share.

*Easy to get wrong:* a contract forbids; it does not require. The two core contracts do not name `sentinel.screening`, `sentinel.ephemeris`, `sentinel.adapters` or `sentinel.ai`. Nothing in the core imports them today, but only a contract line would keep it that way. The technical guide says the same under "Modules and their allowed dependencies".

### The test ladder

The risk engine was built down a ladder of pytest markers, `tier1` to `tier6`: geometry, the integral, NASA's cases, dilution, refusals, the output contract. Each rung failed before the code that satisfied it. Around the ladder, each test directory proves one thing: `tests/sync/` the hub and edge protocol in one process, `tests/property/` CRDT convergence under a hostile network, `tests/docs/` every interface document against the code. The technical guide's "What each directory proves" has the full table, and [chapter 13](13-guardrails-compliance-mbse.md) the guards.

Two settings shape every test. `pyproject.toml` runs pytest with `--disable-socket`, so a test that touches the network fails. And the suite must report **0 skipped**: a skipped test is a claim nobody checked.

## Try it

Set up once, from the repository root:

```bash
export PATH=$HOME/.local/bin:$PATH
uv sync --locked --python 3.12 --extra dev
make help
```

`make help` prints one line per target. Look for the three kinds: runners (`serve`, `demo-local`, `ddil`), generators (`report`, `trace`, `compliance`, `openapi`, `ai-eval`) and release steps (`bundle`, `airgap-local`).

**The engine alone, no node.** One real NASA CDM, TERRA against a fragment of Iridium 33:

```bash
uv run sentinel assess fixtures/cara/PcTestCaseCDMs/000025994_conj_000037558_20210324_151047_20210323_154356.cdm
```

Look for four things: the method in brackets after the Pc, the line starting `DILUTED`, the originator's own Pc labelled `(not Sentinel's)`, and the `inputs` hash that ties the number to its inputs.

**The codec alone.** A NASA sample with a unit-label anomaly:

```bash
uv run sentinel cdm parse fixtures/cara/SampleCDMs/AlfanoTestCase01.cdm
```

The message is accepted with three `UNIT_LABEL_ANOMALY` warnings. That is the incomplete-input path: recorded, not fatal, because Sentinel recomputes those fields from the states.

**One node.** `make serve` builds the console and starts a standalone node on :8000. It needs the web dependencies (`make install`), and :8000 must be free. For the API alone on another port:

```bash
uv run sentinel serve --port 8150
```

In a second terminal:

```bash
curl -s http://127.0.0.1:8150/api/node | python3 -m json.tool
curl -s http://127.0.0.1:8150/api/events | python3 -m json.tool | grep -E '"(event_id|band|verification)"'
curl -s 'http://127.0.0.1:8150/api/events?scope=past' | python3 -m json.tool | grep -c '"event_id"'
```

In `/api/node`, `role` is `standalone` and `modules` has no `sync`. The active events are the exercise scenario, each with `verification` `LOCAL`: this node's own data. The past events are NASA's reference library, loaded at start-up. Without a built console, `/` answers 404 and the API still works. Stop the node with Ctrl-C.

**Two nodes.** `make demo-local` fetches the pinned `nats-server` and `toxiproxy` (`make tools`), builds the console, and starts a hub on :8000 and an edge on :8001. Then compare the two:

```bash
curl -s http://127.0.0.1:8000/api/node | python3 -m json.tool | grep -E '"(node_id|role|hub_id)"'
curl -s http://127.0.0.1:8001/api/node | python3 -m json.tool | grep -E '"(node_id|role|hub_id)"'
curl -s http://127.0.0.1:8001/api/events | python3 -m json.tool | grep -E '"(event_id|verification)"'
```

Same code, same version, different roles. On the edge every event reads `VERIFIED`: its CDMs came over the link and the edge's own engine reproduced the hub's result. Open both consoles side by side; `docs/demo-script.md` is a guided walk.

**The architecture check.**

```bash
uv run lint-imports
```

It prints each contract by name with `KEPT`, then `Contracts: 11 kept, 0 broken.` Try breaking one in a scratch branch: add `from sentinel.conjunction import policy` to `sentinel/sync/agent.py` and run it again. It reports `1 broken`, names the contract ("Sync, CRDTs and operator data know nothing about any mission module") and prints two chains: the direct import of `sentinel.conjunction`, and the indirect one to `sentinel.risk` through `policy`. Revert the line afterwards.

**The test ladder.**

```bash
uv run pytest -q -m tier1                     # one rung: frames and geometry, no probability
uv run pytest tests/sync/test_hub_edge.py -v  # a hub and an edge in one process
uv run pytest -q                              # everything; the summary must show 0 skipped
npm --prefix web test                         # the console (needs make install)
make typecheck                                # mypy: strict on the core and risk
```

The whole Python suite runs in a minute or two. Read the last line: passed, one expected failure (`xfailed`, an open gap recorded in `SECURITY.md`), and no `skipped`.

**Real processes.** One DDIL scenario on a real hub and edge:

```bash
uv run python -m harness.run recovery
```

It starts two NATS servers, Toxiproxy and two nodes on free ports, cuts the link, writes a note on the edge, reconnects over an 8 kbit/s link and checks the note reaches the hub. Each assertion prints `[PASS]` or `[FAIL]`. The result lands in `harness/results/`, which git ignores; only `make ddil`, with all six scenarios, rewrites the committed report.

## Design choices

**A modular monolith with a bus (ADR-004).** One package runs as one process per node, and modules talk through the `Bus` protocol.
- *Buys:* a node deploys to an air-gapped site as one signed bundle and serves its operator with nothing beyond its own host. The same module code runs in-process in tests and over NATS in the field.
- *Costs:* a node's modules scale and deploy together, not one at a time.
- *Rejected:* microservices at the edge, Kafka (a JVM and a quorum), plain MQTT (no request/reply, no leaf model), and direct calls with no bus.

**The CDM as the internal contract (ADR-001).** Every conjunction, whatever its source, reaches the engine as a CCSDS CDM.
- *Buys:* a new source is one adapter, and the engine has one input format that NASA's own files exercise.
- *Costs:* whatever a source knows beyond the CDM stops at the seam, and Sentinel maintains its own codec.
- *Rejected:* a bespoke JSON schema; passing source payloads through.

**Role by configuration, not by build.** Hub, edge and standalone differ only in environment variables read by `sentinel/api/settings.py`.
- *Buys:* one artefact to sign, test and install; the harness tests exactly what ships.
- *Costs:* every node carries code it may not run, such as the sync agent on a hub.
- *Rejected:* separate hub and edge builds, which would double the release and verification path.

**Each node serves its own console (ADR-009).**
- *Buys:* an edge operator keeps a working console with the hub unreachable.
- *Costs:* every node is a web server to patch and harden.
- *Rejected:* one central console, which goes dark exactly when the link does.

**Boundaries enforced by a tool, not by convention (ADR-004, ADR-008).**
- *Buys:* "sync knows nothing about conjunctions" is a CI failure, not a code-review hope. The pass module landed with no change to the core, and a fixed commit range proves it (`CLAUDE.md`).
- *Costs:* a contract to update when a package is added, and occasionally a callback where a direct import would be shorter.
- *Rejected:* documentation-only layering.

Every ADR is in [`docs/system-design.md`](../system-design.md), each opening with what it buys and what it costs.

## How it fails

At this altitude, the question is what each layer does when something it depends on is missing. The answer is always the same shape: say so, keep what still works, and never hide it.

| What is missing or wrong | What happens | Where it shows |
|---|---|---|
| A CDM is wrong (a position labelled in metres, a partial covariance) | Quarantined with a stable code; HTTP 422; never assessed | `GET /api/quarantine`; the `node.<id>.cdm.rejected` event; [chapter 3](03-cdm-and-events.md) |
| The engine's model does not apply | `Method.REFUSED` with a reason and the tripping value; never a zero | The console's "Pc refused" and the reason chip; [chapter 2](02-risk-engine.md) |
| The link to the hub | The edge keeps serving its console from local data. The link is *measured* DENIED | `GET /api/link`; the LINK chip; [chapter 6](06-bus-and-links.md) |
| A setting has a bad value | The node refuses to start. `SENTINEL_ROLE=relay` stops it with `ValueError: SENTINEL_ROLE must be one of hub, edge, standalone` | The process exit and its traceback |
| `nats-server` is not up | A node with `SENTINEL_NATS_URL` retries 60 times, logging `Waiting for nats-server`, then fails to start | The node log |
| No built console | `/` answers 404; the API still works | `make web` |
| The harness binaries | The harness exits naming the missing file and `make tools` | `harness/cluster.py` |
| An import crosses a boundary | `lint-imports` names the broken contract and the chain | CI |
| A document names a path, target or number that no longer exists | `tests/test_docs.py` fails | CI; [chapter 13](13-guardrails-compliance-mbse.md) |

Notice what is *not* in the table: a silent fallback. There is no default covariance, no guessed hard-body radius, no "last writer wins". Where Sentinel cannot answer, it says which input stopped it.

## Check yourself

1. A colleague asks where the hub code is. What do you tell them?
   <details><summary>Answer</summary>There is none separate. A hub is the same package with `SENTINEL_ROLE=hub`. The difference is in the `lifespan` hook of `sentinel/api/app.py`: a hub starts `SyncServer`, an edge with a hub id starts `SyncAgent`, and a standalone node starts neither.</details>

2. The hub's link to an edge goes down. Why does the edge operator's console keep working, and what stops it quietly showing stale hub numbers as current?
   <details><summary>Answer</summary>The edge serves its own console from its own store (ADR-009), and its node talks only to its local `nats-server`, so the lost leaf link breaks nothing local. The link state is measured from sync's own exchanges, so the console shows DENIED. And hub numbers are never shown as the edge's own: an event is VERIFIED only after the edge's engine reproduced the hub's result.</details>

3. You want the sync agent's log lines to include each event's band. Why can't `sentinel/sync/agent.py` import `sentinel/conjunction/policy.py`, and what does the design offer instead?
   <details><summary>Answer</summary>`sync-is-mission-agnostic` forbids `sentinel.sync` from importing any mission module, so that a new module never edits the core. Sync sees only the generic summary fields (`e`, `dl`, `q`, `c`). If sync needs more, the mission module must put it in its summary or expose it through the `ReferenceRecords` protocol; the band belongs in the conjunction module's own logs.</details>

4. A new data source delivers standard CCSDS CDMs. Which code must change for Sentinel to use it?
   <details><summary>Answer</summary>None in the engine or the services. Post the bytes to `POST /api/ingest/cdm` or call `ConjunctionService.ingest`. That is ADR-001's point: the CDM is the seam. Only a source that delivers another shape needs an adapter, and it must produce a CDM.</details>

5. Why does the README never state a Pc threshold as physics, and where do the thresholds live?
   <details><summary>Answer</summary>The bands and the commit point are operator assumptions, not results. They live in `ConjunctionPolicy` in `sentinel/conjunction/policy.py`, are reported by `GET /api/node` under `policy`, and are labelled as assumptions wherever they are shown. The engine computes the Pc; the policy sorts it.</details>

6. After `make ddil` a number in `docs/ddil-results.md` changes. What fails, and why is that the right behaviour?
   <details><summary>Answer</summary>`tests/test_docs.py` fails for every prose quote of that number registered in `tests/doc_claims.toml`. A document cannot silently disagree with the measurement it cites; you update the prose and the registry together.</details>

7. You add a mission module, `sentinel/<name>/`, with code but no `__init__.py` docstring. Which check fails, and what else should you add before it touches sync?
   <details><summary>Answer</summary>`test_every_package_has_a_module_docstring` in `tests/test_docs.py`. Before it syncs anything, give it its own import contract and add it to the forbidden lists of `core-is-mission-agnostic` and `sync-is-mission-agnostic`, as the technical guide's recipe (a) says.</details>

8. Why does `sentinel/triage/` exist as a package when it is one short file?
   <details><summary>Answer</summary>It is the whole vocabulary the core has for urgency: a priority class, a deadline and a consequence, and the order over them. Keeping it separate lets sync order records from any mission without importing one, which is what the core contracts protect.</details>
